### Frozen-core issues (NOT modified — documented only, with boundary coverage)

1. **`ActionExecutor` retry path is not atomic** — retry scheduling persists
   `saveExecution(execution)` and `save(action)` as two calls; completion and
   terminal failure use the atomic `persistExecutionOutcome`. Boundary tests
   (`ActionExecutionWorker.test.ts`, `ActionExecutor.test.ts`) already cover
   retry semantics. A repository-level transaction is the safe fix point.
2. **`ActionExecutor` logs via `console.log('[EVENT] ...')`** (frozen) instead
   of the structured `Logger`; `ActionExecutionWorker` uses `console.warn`.
3. **`redactSensitiveData` (frozen `ActionApplicationService`) redacts
   `idempotencyKey`/`externalId`** in execution event logs; the non-frozen
   `Logger` was refined instead (F33).
4. **`ActionExecutor` timeout timer is not cleared when the adapter wins the
   race** — the 8 s `setTimeout` remains armed after a successful execution
   (harmless: the race is settled, but the timer keeps the event loop alive up
   to 8 s after shutdown). Frozen; document-only.
5. **`AuthRateLimiter` is single-process in-memory** — documented limitation
   of the supported single-process architecture.

## G. H7 telemetry verification (real PM telemetry path)

Where real PM telemetry **enters the system**:

1. `RecommendationsPanel` mounts the detail view → `decisionWindowRef = { presentedAt: Date.now(), startedAt: Date.now() }` — the recommendation is presented to the PM (real client timestamp).
2. PM clicks **Approve & Execute** → `handleApprove` → server approval (`POST /api/actions/approve`, idempotent) → `apiClient.recordDecision(...)` with `decisionCompletedAt: new Date().toISOString()` and the stored window.
3. `POST /api/projects/:id/decision-telemetry` validates (auth → membership → project-scoped recommendation lookup → ISO timestamps → start ≤ completion) and calls `APEXProductService.recordPMDecision`.
4. Server computes `originalH3Score` (persisted) and `calibratedH6Score` (calibrator) itself — **the client can never fabricate scores**; the client supplies only its real decision window and decision kind.
5. `PMDecisionTelemetryService` validates the record, computes `overrideOccurred`/`overrideDelta` = |H6 − PM priority| / rank displacement, and persists with a deterministic id `pmd-{sha256(workspace\|recommendation\|decisionStartedAt)}` (duplicate submissions collapse).

Where it is **persisted**: `DurableFileDatabase.pmDecisionTelemetry` (JSON
store, atomic commit), read back through `SqlProductRepository.getPMDecisionTelemetryByProject`
and `mapPMDecisionTelemetryFromDb` (Date reconstruction).

Where it is **consumed**: `ProductValidationService.measuredDecisionLatencySeconds`
= mean(`decisionCompletedAt − decisionStartedAt`) over records with
`ms >= 0`; epistemic state `observed` only when ≥1 record exists, else
`unavailable`. Latency is **not** hard-coded, simulated, random, or derived
from polling intervals.

**Live E2E record (this audit):** signup → workspace → connect repo →
analysis (`completed`, 8 ms) → 1 recommendation (`rec-add-ci-...-proj-core-no-ci`,
score 13.3) → approve (200, `approved`) → re-approve (same id) → outcome
created (`PENDING`) → telemetry recorded (`pmd-5677…`, `originalH3Score 13.3`,
`overrideOccurred false`) → product-value showed `measuredDecisionLatencySeconds
{value: 10, epistemicState: observed, observationCount: 1}` (10 s window) →
outcome verified `VERIFIED_SUCCESS` with real CI evidence → decision-metrics
`{totalApproved: 1, successRate: 100, unverifiableRate: 0}` → profile compiled
(`h6-v1`) → calibration `{baseScore: 13.3, calibratedScore: 13.3}` → second
project analyzed in the same workspace without clobbering project 1 (F-A2) →
cross-tenant 403s → logout → session 401.
